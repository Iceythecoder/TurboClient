# Reactive Olm agent: current implementation and validation

## Click-path correction and bomb/electric hazards

The supplied screenshots show Combat Options while the controller is waiting for Inventory, and Inventory while it is waiting for Prayer. The installed mouse helper and stretched-mode translator were inspected directly. Two incompatibilities were reproduced against that actual translator without dispatching inputs: unscaled widget coordinates translate to the wrong game point, and the old helper's String event source triggers a `ClassCastException` where the stretch listener requires a Component.

Visible interface clicks now convert logical widget coordinates to the stretched canvas size when stretching is enabled. They use Canvas-source primary-button events dispatched on the AWT event thread, with focus/showing guards, rather than the incompatible helper. No tab-opening client script or forced selection variable is used. Selection and panel visibility must still acknowledge the change. The selector also restricts buttons to the active fixed/resized/stacked layout and rejects hidden ancestors. Failed button lookup remains a retriable observation state instead of throwing out of the prayer observer. Chatbox widget clicks share the correction.

Bomb and electric hazards are separate from flame walls. Enabled installed-library candidate signals are `ObjectID.CRYSTAL_BOMB` (29766), `GraphicID.OLM_LIGHTNING` (1356), and the library's lightning object variants 16190/16191. Crystal-bomb and electric-wall/lightning NPC/object names can also supply a candidate; configurable `bombObjects/bombNpcs/bombGraphics` and `electricObjects/electricNpcs/electricGraphics` cover Orion variants. These mappings are API candidates, not IDs proven from the photographs. They are confined to the current configured/provisional encounter area and can be disabled with `useInstalledSpecialSignals`.

Bomb avoidance defaults to the user-specified four-tile radius. When threatened, the local collision-checked search can find an outside endpoint beyond an adjacent tile; execution uses normal native pathing, without changing movement speed. If the full radius cannot be escaped in one available route, a step reducing aggregate bomb proximity may be chosen while excluding other hard hazards. Electric segments get a one-tile avoidance buffer by default; the controller can leave that buffer and excludes routes through observed electric tiles. It never treats them as clickable flame walls. Ordinary approach paths also exclude known hazards.

The defaults are configurable through `bombRadius` (1..8) and `electricRadius` (0..2). Bomb deadlines, Orion blast radius, and future electric-wall motion are not established. Current avoidance uses observed hazards and a buffer, not a claimed accurate prediction. Variant IDs still require live confirmation; a photograph alone does not establish which API event produced it.

`OlmUiHazardTests` exercises the installed stretch translator for the old failure and every corrected click phase, plus active-layout filtering, hidden ancestors, radius escape, electric lanes/buffer and learning export compatibility. Automated build checks pass. Live tab switching and hazard avoidance remain unverified; the supported desktop helper was attempted and is still unavailable.

## Current Inventory → Prayer transaction

Tab readiness now requires **both** the selected tab and visible content. The installed `Tabs.isOpen` implementation was inspected: it compares client varc integer 171 with the tab's enum position. `VisibleCombatUi` performs that same check through the supplied Client, then checks the required panel. The previous visibility-only rule could classify cached inactive widgets as ready; the earlier visibility-only test was insufficient and is replaced by a regression in which both cached panels report visible but only the selected tab is allowed to act.

`OlmGearBatch` now tracks the Inventory transaction independently of equipment acknowledgements and offensive prayer actions. It submits at most four missing items per observed game tick, one per client update, targeting an eight-item switch over two ticks. It waits for a usable initial tick window, skips already worn/pending items, and retains progress while urgent defense interrupts. More than eight missing items require additional ticks. Interruptions and delayed acknowledgements can extend the transaction; the status reports when the two-tick target is exceeded and recovery continues.

Once the combat gear requests have all been submitted, the Prayer/verification phase may open Prayer and request the configured offensive boost while awaiting final equipment acknowledgement. Attack output still requires observed equipment confirmation. Entry separately retains its required protection and magic boost checks. Incoming-projectile protection remains independently prioritized and may interrupt an Inventory batch; an offensive boost does not select a protection style based on the player's weapon.

The combined synthetic regression starts on Prayer with both cached panel widgets visible, opens Inventory, submits eight items in two actual tick numbers, opens Prayer, and submits protection then Augury on separate client updates. It also checks late-tick deferral, per-tick item limits, acknowledgement waiting and style changes. This validates scheduling with collected synthetic inputs, not live acceptance or live two-tick completion in Orion. These rules supersede the earlier unrestricted per-client gear pacing described below.

## Current entry, tab switching and phase transitions

The user's latest entry instruction is to finish all visible dialogue instead of depending on a particular coloured chat message. There is no chat-message classifier or chat logging in this implementation. Entry handles Begin, Continue/Space, and further entry options while deferring gate clicks. A short empty gap between dialogue pages does not cause a gate click: the chatbox must remain clear for 35 client cycles before another entry attempt. Entry options that explicitly leave/cancel/abandon are excluded. Continued messages after the second gate preserve the awaiting-crossing state; they do not reset the sequence to the first gate. Observed automatic crossing after dialogue can also finish entry without an unnecessary gate click.

`VisibleCombatUi` verifies actual Inventory and Prayer content visibility rather than relying solely on the installed selected-tab variable. Pending tab changes have a short coordination window: routine gear actions cannot reverse a still-opening Prayer tab; urgent defense can supersede an ordinary Inventory opening. Equipment, boosts, supplies and defense all use this shared gate. Ordinary movement no longer prevents gear/boost preparation; attack output still yields to a mechanic that requires movement or holding position.

Hand targeting now consumes actual NPC death events and excludes dead actors even if their previous health bar remains cached. A melee hand outside melee range produces explicit collision-checked approach movement even without a nearby hazard. The NPC role determines style, independently of which side of the screen the hand occupies.

After a confirmed pair of hand deaths in a nonfinal transition, the fighter prepares MAGIC equipment and the configured magic boost. `OlmArenaPlan` derives approach positions for both mirrored mage spawns from repeated mage-attack examples in the user's selected second demonstration. Once the magic setup is observed active, the existing hazard/collision controller moves toward the recorded opposite approach. It reacquires the new live hand instead of attacking an absent/predicted NPC. Final hand completion retains the existing Ranged head phase. The numeric approach map is included in explicitly saved profiles/presets; older setups load it from the selected local demonstration when available. Missing geometry is reported, not invented.

Tests cover multi-page and second-entry dialogue, transient empty chatbox gaps, actual panel visibility, urgent tab priority, mage-to-melee target selection, approach movement and either mirrored direction. Replay of the actual selected recording produced two supported mage approach positions. This validates extraction on that recording, not live path traversal or encounter completion.

## Foundation correction after the failed test

Entry now requires confirmed potting, observed MAGIC equipment, active Protect from Magic and the configured active magic boost (default Augury) before any gate/confirmation step. These conditions are rechecked after ignored interactions. A different mapped incoming attack retains defensive priority while waiting outside. A missing/disabled magic boost holds entry with an explanation instead of claiming readiness.

Gate entry retains the gate → visible Begin the raid → observed chatbox dismissal → second gate → observed movement/room evidence protocol. Ignored gate actions are retried. An ignored confirmation click uses the installed `Dialog.chooseOption(number)`, whose inspected implementation types the numbered option through the keyboard API. The number is obtained only from the visible, uniquely matching option; a reordered Begin option uses its actual number, and unrelated/ambiguous dialogue never receives a guessed `1`. A matching numbered option also permits confirmation when widget click bounds are unavailable. Request counts are shown separately from observed progression.

Gear switching uses `OlmGearSwitch` to issue each missing, nonpending item on successive client updates through the shared visible Inventory gate. It does not wait for each item's equipment acknowledgement before issuing the next item. Full equipment confirmation is still required before combat/entry. A synthetic regression submits seven items over seven client cycles while all equipment acknowledgements remain pending; this demonstrates no per-item game-tick pacing delay, not live same-tick acceptance by Orion. Actual request traces include client cycle and game tick.

The earlier action path incorrectly used attack input time as an attack cooldown boundary. It could therefore walk immediately after requesting an attack and cancel it before it happened. `OlmAttackTiming` now separates requests from configured local attack animations. Only observed configured animations start weapon cooldowns. Optional between-attack walking is suspended until a known animation is observed, and is never allowed in the observed attack tick. Explicit hazard escape remains active. Animation IDs/speeds can be supplied through the profile's `attackAnimations` map or the existing shared verified animation settings; no unobserved animation is assigned an attack meaning.

Movement and wall clicks now share the visible-action budget with prayers and inventory operations. Optional cooldown walking is limited to one request per observed game tick. The native server movement rules remain unchanged.

Potion cooldown now starts at the tick where the inventory actually shows a consumed dose. The previous subtraction of one acknowledgement tick could send a subsequent sip early when request phases changed. The conservative three-tick wait can add one request tick when acknowledgement is delayed; there is no claim that delayed inventory state is the precise server consumption timestamp.

The shared tick clock estimates observed event interval using a bounded median after three samples, initially 600 ms. It ignores duplicate tick numbers and divides missed-event gaps by their tick count. This measures arrival spacing, not the server's hidden clock or network latency. Weapon and potion cooldowns remain based on actual game tick numbers. The dashboard now displays the current action/wait reason directly; Advanced status includes the attack clock and observed tick interval.

`OlmFoundationTests` exercises ignored and delayed sips through the complete seven-dose preparation sequence, duplicate/missed ticks, and the attack-request/walking cancellation failure. These are synthetic controller tests. They do not certify that the live pre-pot or whole encounter works.

The new encounter specification is being applied incrementally to the existing companion. This update implements the first projectile/prayer evidence milestone and repairs the existing combat action path. It is not a claim that the complete encounter specification is implemented or that an Orion kill has been validated.

## What changed

- `ChambersController` continues observing and checking defensive prayer on projectile/client events independently of the combat sequence. Earliest estimated impact controls protection. A different, earlier threat can supersede a pending request on the next client cycle.
- Acknowledged defensive prayer now releases the previous retry lock, allowing immediate restoration if prayer is subsequently disabled. An unacknowledged toggle is not repeatedly sent, which could otherwise toggle a delayed activation off.
- After a defensive request is submitted, routine work may continue if impact is still outside the safety margin. An unsent request or unconfirmed protection close to estimated impact retains priority. The visible UI action budget prevents routine inputs overwriting a prayer request in the same client cycle.
- Removed Olm's extra two-client-cycle pacing delay. The client-event/UI budget serializes inputs. Actual potion cooldown, equipment confirmation, weapon speed, prayer confirmation, and error backoff remain.
- Existing basic combat now requests Augury for Magic, Piety for Melee/special, and Rigour for Ranged/head by default. These are configurable through `offensivePrayers` and `offensivePrayersEnabled` in the profile and persist in presets. Only style boosts or `NONE` are accepted; protection prayers cannot be supplied as offensive prayers. Actual activation is checked. Missing/unconfirmed boosts release DPS after 35 cycles and defer retries for 300 cycles; this does not claim that a prayer unlock exists.
- `OlmPrayerLearning` retains up to 128 numeric projectile outcomes and cumulative timing metrics. It records requested/observed activation, late or missing near-impact observations, unknown classifications, conflicting flights and local damage totals. No chat, player names or screenshots are captured.
- Acknowledgement latency increases the safety margin conservatively. Observed inactive protection near estimated impact increases it; 20 clean observations permit gradual reduction, bounded by measured acknowledgement delay. Configured minimum margin still applies. The controller already switches immediately: learning cannot make detection precede an available event or remove server delay.
- Timing survives subsequent attempts in memory and is included in explicit learned presets. **Advanced settings → Projectile prayers → Save prayer timing...** also permits exporting after an unsuccessful run; **Load prayer timing...** restores validated statistics and disarms outputs for explicit re-arming. Existing exports are preserved. Incomplete files created by a failed save are cleaned up.

## Evidence and limits

`HitsplatApplied` exposes a local damage amount, not the responsible projectile or server protection check. Consequently:

- A prayer request is not confirmation; `isPrayerActive` is confirmation of state only.
- Active prayer sampled one cycle before estimated impact is labeled `ACTIVE_NEAR_ESTIMATED_IMPACT`, not successful damage protection.
- Missing the observation window is unobserved, not a win or failure.
- Damage is recorded with cause unassigned. There is no invented per-projectile reward or automatic reclassification from a single hit.
- Death analysis reports available timing evidence and explicitly leaves cause unassigned when attribution is unavailable.
- Simultaneous incompatible prayers cannot both be guaranteed. Strict prayer-only mode disarms; tolerant combat continues deterministic earliest-impact handling, without a fabricated expected-damage model.

The baseline retains the prior conservative 70 actual HP floor, recorded preparation sequence, native gate → Begin the raid → gate entry flow, existing mechanics handlers, and limited neural target learner. It does not yet implement a unified lethal-hazard/prayer deadline scheduler, authoritative damage prediction, all listed special handlers, healing/invulnerability recognition, learned arbitrary phase counts, or full combat reinforcement learning. These require additional Orion observations and separate validation. The NH simulator's accelerated PPO training is not being represented as live Orion training.
